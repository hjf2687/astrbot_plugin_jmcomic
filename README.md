# JMComic 下载插件

为 AstrBot 提供漫画下载功能，下载后自动转换为 PDF 发送。

## 使用方法

```
jm350234        下载整本漫画并转成 PDF
jm摇号          从每日推荐里随机摇一本
jm摇号 全彩     按关键词随机摇一本
jm停止          停止全部下载，已下好的图保留（可续传）
jm暂停          同 jm停止
jm停止 350234   只停这一本
jm放弃          停止全部下载，并删掉已经下好的图
jm取消          同 jm放弃
jm放弃 350234   只放弃这一本
jm / jmhelp     显示帮助
jm帮助 / jm指令  同 jmhelp
```

## 怎么知道有哪些指令

三个地方：

1. **群里直接发 `jm`**（或者 `jmhelp`、`jm帮助`、`jm指令`）就会回一份帮助。
2. **AstrBot WebUI → 插件管理 → JM漫画下载 → 详情页**：会列出这个插件注册的每一条
   指令/正则和它的描述。
3. **AstrBot WebUI → 管理行为 → 指令**：全部指令的总表，能看到描述、别名、权限、
   启用状态，还能在那里改名、加别名、改权限、单独停用某条指令。

### 唤醒词那点事

AstrBot 有两类过滤器，规则不一样（`astrbot/core/star/filter/regex.py` 里有明确注释）：

| 类型 | 受 `wake_prefix` 制约 | 本插件用到的地方 |
| --- | --- | --- |
| `@filter.command` 标准指令 | **是** | `jmhelp` |
| `@filter.regex` 正则 | **否** | `jm350234`、`jm摇号`、`jm停止`、`jm`… |

你现在的唤醒词是 `妃雨`。所以：

- `jm350234`、`jm摇号`、`jm停止`、`jm` 这些**群里直接发就行**，不用带唤醒词。
- `jmhelp` 这条标准指令本来要发 `妃雨jmhelp`（或者 @ 机器人）才会触发。
  因为这个坑太容易踩，插件额外挂了一个正则版的帮助，所以**群里直接发 `jmhelp` 也有效**。

## 配置

所有配置都在 AstrBot 的「插件配置」面板里改，改完自动生效，不需要重启。

> 面板里的标签是**单行截断**的（AstrBot 的插件配置面板没有悬停提示），所以标签写得
> 很短。完整说明看下面这张表。

| 配置项 | 面板上的标签 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `proxy` | HTTP 代理，留空 = 直连 | 空 | **留空 = 直连**，会显式禁用系统代理和环境变量里的 `http_proxy`/`https_proxy`。要挂代理填 `http://127.0.0.1:7890` 这种 |
| `threads` | 图片并发数，默认 4 | 4 | 单本漫画的图片并发数，和 JM桌面端一致。网差调小到 2，网好可调到 8 |
| `retry_times` | 单域名重试次数 | 3 | 单个请求在同一个域名上失败后的重试次数，超了会自动换下一个域名 |
| `timeout` | 请求超时（秒） | 30 | 单个请求的读取超时（秒）；连接超时固定为它的 2/3，且不超过 20 秒 |
| `custom_domains` | 自定义接口域名 | 空 | 自定义接口域名，多个用英文逗号分隔；留空则自动获取官方域名列表 |
| `pdf_quality` | PDF 图片质量，越低越小 | 85 | 把 WebP 转成 JPEG 时的质量，50~100。详见下面「PDF 为什么大」 |
| `keep_images` | 生成 PDF 后保留原图 | 关 | 生成 PDF 后是否保留原始图片。关掉更省空间，打开则下次下载可以复用已下好的图 |
| `pdf_cache_limit` | PDF 缓存上限 | 50 | `temp/` 目录最多保留多少个已生成的 PDF，超出的按最久未使用删除 |
| `progress_at` | 在完成百分之几时报进度 | 50 | 里程碑式进度提示，见下节。留空 = 只发开始和结束两条 |
| `encrypt` | 给 PDF 加密码后再发 | 关 | 开启后发出去的是**带打开密码的 PDF**（AES-256），见下节 |
| `encrypt_password` | 加密密码 | 空 | 上面的开关打开后**必填** |

> 面板上标签是**单行截断**的，所以标签写得很短；每个配置项的完整说明写在标签下面
> 那行小字里（AstrBot 的插件配置面板会渲染 `hint` 字段并自动换行）。

## 加密（可选）

打开 `encrypt` 并在 `encrypt_password` 里填一个密码，发出去的 PDF 就带打开密码了
（AES-256，用 `pypdf` 实现，图片流原样搬运，体积只涨 0.1%）。没密码打不开——
群里的预览、转发、随手点开都看不到内容。

**开了加密但密码栏是空的，插件不会发文件**，只会回一句提醒。这是故意的：既然开了
加密，静默降级成明文是最危险的失败方式。代价也不大——漫画已经下好了，
**填完密码再发一次同样的命令就直接出加密版，不会重新下载**。

改密码同理，改完重发一次即刻生效。


## 进度提示

下载过程中只在**里程碑**上说话，不按时间刷屏：

- 发命令后立刻回一条「漫画 X 正在火速下载~」
- 下到 `progress_at` 里的百分比时报一次（默认只在 **50%** 报一次），带张数和百分比
- 图片下完、开始拼 PDF 时报一次
- 最后发结果（PDF 或错误）

`progress_at` 可以填多个，逗号分隔（中文逗号也行），例如 `25,50,75`；填 `0` 或留空
就一条进度都不报，只剩开始和结束。

> 为什么要这个：原版把网络请求直接跑在 AstrBot 的事件循环上，一卡 30 多秒，
> 期间整个机器人是僵住的，用户完全不知道发生了什么。现在既不会卡，也能看到进展。

## PDF 为什么大 / 怎么调小

**先说结论**：禁漫的图是 WebP，而 WebP 不是 PDF 支持的图像格式。img2pdf 遇到 WebP
会把它解码成裸 RGB 再用 FlateDecode **无损**塞进 PDF，体积能涨好几倍。v2.3.2 之前
就是这个行为。v2.3.3 起改成「先把 WebP 转成 JPEG，再交给 img2pdf」，并且本来就是
JPEG 的图原样沿用、不重新编码。

拿实际的一本（47 页，1280×1706 全彩）量过：

| | 单页 | 全 47 页 |
| --- | --- | --- |
| 修复前（WebP 无损塞进 PDF） | ~2190 KB | **88.8 MB** |
| 修复后 `pdf_quality=85` | ~429 KB | **约 18 MB** |
| 修复后 `pdf_quality=75` | ~337 KB | **约 13 MB** |

想更小就把 `pdf_quality` 调低（75 肉眼几乎无差，60 以下开始能看出来）。注意这本是
**全彩插画**，源图本身每页就有几百 KB，PDF 不可能比源图小很多——黑白漫画会小得多。

## 下载失败了怎么办

直接再发一次同样的命令就行：

- 已经下好的图片不会重下，只补缺的那些。
- 补齐之后才会生成正式的 PDF；缺页时生成的是 `temp/<漫画ID>.partial.pdf`，不会污染缓存。
- 如果想让它一直保留原图方便续传，把 `keep_images` 打开。

## 下到一半不想下了

```
jm停止           保留已经下好的图，再发一次 jm<ID> 从断点接着下
jm暂停           同 jm停止
jm停止 350234    只停这一本
jm放弃           停止并把已经下好的图删掉
jm取消           同 jm放弃
jm放弃 350234    只放弃这一本（没在下载时会把之前留下的图也清掉）
```

**停止不是瞬时的**：已经在线路上的那几张图没法中断（`curl_cffi` 的请求是阻塞调用），
只能等它们自己结束——正常情况下几秒，最坏一个请求超时（默认 30 秒）。
排队中还没开工的图会立刻被丢掉，不会再发请求。

拼 PDF 那一步不响应停止（都到最后了，停不停没意义）。

## 并发是怎么安排的

一共两层，别混淆：

| 层 | 在哪 | 默认 | 说明 |
| --- | --- | --- | --- |
| 同时下载的**本子**数 | `main.py` 的 `DOWNLOAD_WORKERS` | 2 | 固定值，不在配置面板里 |
| 单本内部的**图片**并发数 | 配置项 `threads` | 4 | 和 JM桌面端 `settings.json` 里的 `threads` 一样 |

所以最坏情况是 `2 × 4 = 8` 个图片请求同时在跑。JM桌面端是每本 4 个（`max(1, min(8, threads))`），
本子之间不设上限（由界面一次提交一个）。

对比一下原来的实现：`option.yml` 里根本没写并发，走的是 jmcomic 的默认
`download.threading.image = 30`，也就是单本一次开 30 个线程。弱网下这么多连接互相挤，
超时和失败反而更多——这是「总是下载出错」的成因之一。

### v2.3.3
- **修掉 PDF 体积暴涨**。`img2pdf` 不认 WebP，会把图解码成裸 RGB 再用 FlateDecode
  无损塞进 PDF——实测 47 页的本子出了 **88.8MB**。现在先统一转成 JPEG 再交给
  img2pdf；本来就是 JPEG 的图**原样沿用**，img2pdf 无损直嵌，不重新编码。
  同一本实测：88.8MB → 约 18MB。
- 新增配置项 `pdf_quality`（默认 85），控制 WebP→JPEG 的质量；调到 75 大约 13MB。
- 自检脚本加了体积用例：既钉住「直接喂 img2pdf 会膨胀 14 倍」这个坑，也验证
  修复后体积不膨胀、且 PDF 里用的是 DCTDecode。

### v2.3.2
- **修掉「改了 jm_service.py 重载后不生效」**。AstrBot 重载插件时只清理 `sys.modules` 里以
  `data.plugins.<插件目录名>` 开头的模块（`star_manager.py:721`、`:730-737`），而
  `main.py` 原来用 `sys.path.insert` + `from jm_service import ...`，模块会以**裸名**
  `jm_service` 注册进去，重载时清不掉 —— `main.py` 重新执行了，但拿到的是缓存的旧
  `jm_service`。表现就是：改了 `jm_service.py`、点了重载、报错栈还指向旧行号。
  现在改成用 `importlib.util.spec_from_file_location` 按路径加载，并注册成
  `<插件模块名>.jm_service`，落进 AstrBot 的清理范围；顺带也避免和其他插件的同名
  文件抢 `sys.modules["jm_service"]`。
- 自检脚本加了针对性的用例：造一个假的 `astrbot` 包，把真实的 `main.py` /
  `jm_service.py` 拷进 `data.plugins.astrbot_plugin_jmcomic`，连续加载两次并中途改代码，
  验证第二次确实读到了新代码。

### v2.3.1

### v2.2.0
- **不再阻塞事件循环**：jmcomic 是同步库，之前直接在协程里调用，日志里出现过 5 次
  30 秒以上的 `Event loop stalled`（最长 34.9 秒），期间整个机器人都会卡住。
  现在所有网络请求都跑在线程池里，并每 20 秒回报一次进度。
- **修掉「下载出错」的主因**：原来靠下载前后 glob 求差集来找图片，而 jmcomic 默认
  开启下载缓存、已下好的图不会重下，于是重试时差集只剩没下过的几张 —— 表现就是
  PDF 缺页，或者干脆报「未找到图片」。现在按章节遍历、用
  `option.decide_image_filepath()` 精确算出每张图该在哪，不再靠猜。
- **去掉 Flask 中间层**：不再在 127.0.0.1:5000 起一个内置 HTTP 服务，少一跳、
  少一个常驻端口，也没有了并发请求互相污染下载目录的问题。
- **PDF 生成不再吃内存**：原来把所有图 `convert('RGB')` 后一次性读进内存，
  300 页能吃掉上 GB，一张坏图整个失败。现在优先用 `img2pdf` 直接嵌入原图（快、无损），
  格式不认或没装时回退 PIL，并且逐张处理、单张坏图只跳过那一张。
- **并发数可控**：jmcomic 默认一次开 30 个线程下图片，弱网下互相挤。
  默认降到 6，可在配置里调。
- **请求超时可控**：以前没有超时设置，弱网下单个请求能挂很久。
  现在连接超时不超过 20 秒、读取超时默认 30 秒。
- **代理配置真的生效了**：「留空＝直连」写成空字符串，挡住 libcurl 自己去读
  环境变量代理；client 全局复用，不再每个请求重建（重建一次要多发好几个请求）。
- **发送后不再硬删文件**：原来 `yield` 之后 `sleep(5)` 就删临时文件，
  上传超过 5 秒就会读到已删除的文件。现在直接发缓存目录里的 PDF。
- 新增 `temp/` 缓存数量上限，避免缓存目录无限膨胀。
